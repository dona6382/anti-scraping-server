## 2. AI 에이전트 구성

### Phase 1: 5개 전문 에이전트 (v2.0 ~ v2.5.0)

초기에는 5개 에이전트를 시니어 개발팀처럼 병렬 투입:

| 에이전트 | 역할 | 투입 방식 |
|----------|------|----------|
| TS Code Reviewer | 타입 안전성, 코드 일관성, dead code | 병렬 분석 |
| NestJS Backend Dev | 아키텍처, DI, Guard 체인, 성능 + 구현 | 병렬 분석 + 구현 |
| Security Researcher | 공격 벡터, 암호화, timing attack, XSS | 병렬 분석 |
| Security Test Engineer | 테스트 커버리지, 회귀 방지 | 병렬 분석 + 테스트 작성 |
| Project Manager | 우선순위, 기능 갭, 종합 판정 | REJECT → APPROVE 관리 |

```
[Code Reviewer] ──┐
[Backend Dev]   ──┼── 병렬 실행 ──→ [PM 종합 보고서] ──→ 사용자 판단
[Security Res.] ──┤
[Test Engineer] ──┘
```

### Phase 2: 공격자/방어자 반복 분석 (v2.5.1 ~ v2.6.0)

Phase 1의 교훈을 바탕으로 더 효율적인 방식으로 전환:

| 에이전트 | 역할 | 투입 방식 |
|----------|------|----------|
| **공격자 (Penetration Tester)** | 코드 분석 기반 취약점 탐색, 구체적 exploit 시나리오 | 라운드별 테마 |
| **브라우저 펜테스터** | Playwright headed 모드 실전 공격 | 공격자와 병렬 |
| **방어자 (Security Engineer)** | 발견 이슈 수정 + 방어 로직 강화 | 수정 후 즉시 검증 |
| **PM (Recruiter 관점)** | 프로젝트 전체 품질 평가 | 마일스톤에서만 |

```
🔴 공격 (코드 + 브라우저 병렬) → 🔵 방어 (수정) → 🟢 개선 (강화) → 📝 학습 → 다음 라운드
```

#### 라운드별 테마와 결과

| 라운드 | 테마 | 발견 | 수정 | 핵심 학습 |
|--------|------|------|------|----------|
| R1 | 인증/세션 | HIGH 1 | 1 | Refresh Token을 Access Token으로 사용 가능 → type 검증 추가 |
| R2 | 봇 탐지 회피 | HIGH 2 | 2 | PoW 속도 체크 로깅만 → threat score 반영, MIN_REQUESTS 10→5 |
| R3 | 인프라 공격 | HIGH 3 | 3 | ACTIVE_IPS O(N)→Set, Canvas CPU 제한, ipLocks 5K cap |
| R4 | 복합 공격 | CRITICAL 1 | 1 | **렌더링 한도 → 빈 CAPTCHA → 검증 스킵 bypass** (수정 간 상호작용) |
| R5 | 최종 펜테스트 | CRITICAL 1 | 1 | puzzleId/Answer 생략 시 CAPTCHA 완전 bypass |
| R6-8 | 전면 재공격 | 0 | 0 | CLEAN — 모든 방어 검증 완료 |

## 3. 사람 vs AI 역할 분담

| 사람 (나) | AI (Claude Code) |
|-----------|-----------------|
| 보안 아키텍처 설계 판단 (8단계 Guard 체인 구성) | 코드 구현 + 테스트 187개 작성 |
| 에이전트 역할/프로세스 설계 (Phase 1→2 전환) | 8+ 라운드 공격자/방어자 반복 분석 |
| 기능 우선순위 결정 (CAPTCHA-for-all 등) | 34건 보안 취약점 발견 + 수정 |
| 실 브라우저 테스트로 런타임 버그 5건 발견 | 브라우저 펜테스트 29개 항목 자동화 |
| 최종 승인/거부 판단 (false positive 검증) | 채용 담당자 관점 프로젝트 리뷰 |
| "AI가 보고한 이슈 중 진짜 유효한 것만 선별" | 공격 시나리오 작성 + 방어 코드 제안 |

### AI가 못 하고 사람이 한 것

| 항목 | 설명 |
|------|------|
| **IPv6 토큰 파싱 버그** | 단위 테스트는 IPv4만 → 실 브라우저(localhost = `::1`)에서 발견 |
| **Cookie URL-encoding** | mock 테스트는 raw string → 실제 브라우저는 `:`를 `%3A`로 인코딩 |
| **fetch() Set-Cookie 미적용** | 단위 테스트에서는 정상 → 브라우저 보안 정책으로 쿠키 미저장 |
| **False positive 판별** | AI가 8+ 라운드에서 보고한 ~50건 중 실제 유효한 34건만 선별 (나머지는 설계 의도, 싱글스레드 특성 미이해 등) |
| **CAPTCHA 난이도 판단** | "사람이 봐도 어렵다" → SVG에서 Canvas PNG로 전환, "봇이 다 풀겠다" → 타이머 10초 + 6글자로 결정 |

### AI의 False Positive 패턴 (사람이 걸러낸 것)

AI가 반복적으로 잘못 보고한 패턴들:

| 패턴 | AI 주장 | 실제 |
|------|---------|------|
| Memory Cache race condition | "두 요청이 동시에 get→delete" | Node.js 싱글스레드 — 동기 코드 인터리빙 없음 |
| HMAC brute force | "쿠키 서명 추측 가능" | SHA-256 + 64바이트 키 = 계산적으로 불가능 |
| Open Redirect | "returnUrl로 외부 사이트 리다이렉트" | pathname만 추출 — hostname 무시됨 |
| CAPTCHA 미표시 | "첫 방문자에게 CAPTCHA 안 보임" | THRESHOLD=0 → 0 >= 0 = true → 항상 표시 |
| safeCompare 버그 | "bufA, bufA 비교는 버그" | 의도적 dummy comparison (constant-time 유지) |

**교훈**: AI 보안 분석 결과를 100% 신뢰하면 안 된다. 사람이 코드를 이해하고 false positive을 걸러내는 것이 핵심.

## 6. 핵심 교훈

### AI 활용

1. **AI는 "시니어 팀"이 될 수 있다** — 단, 역할을 명확히 정의하고 프로세스를 설계해야 한다
2. **AI의 테스트는 Mock 수준** — 실 환경 검증은 반드시 사람이 해야 한다
3. **AI 보안 분석의 ~30%는 false positive** — 사람이 코드를 이해하고 걸러내야 한다
4. **공격자/방어자 반복이 효과적** — 5개 에이전트 병렬보다 2개 에이전트 반복이 더 깊은 분석
5. **수정 간 상호작용 버그가 가장 위험** — R4에서 발견된 CAPTCHA bypass는 이전 수정들의 조합에서 발생

### 프로세스

6. **먼저 직접 돌려보기** — AI한테 "분석해줘" 하기 전에 브라우저 한 번 켜보기
7. **에이전트는 필요한 만큼만** — 문서 수정에 Security Researcher 불필요
8. **수정은 모아서 한 번에** — 건건이 분석하지 말고 묶어서 1회
9. **"이전에 OK 받은 건 넘어가" 프롬프트** — 에이전트는 매번 백지에서 시작
10. **PM 관점 리뷰는 마지막에** — 채용 담당자 관점으로 전체 품질 점검
