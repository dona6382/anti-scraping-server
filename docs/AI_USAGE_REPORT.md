| 에이전트 | 역할 | 투입 횟수 |
|----------|------|----------|
| TS Code Reviewer | 타입 안전성, 코드 일관성, dead code 분석 | ~10회 |
| NestJS Backend Dev | 아키텍처, DI, Guard 체인, 성능 분석 + 구현 | ~10회 |

### 에이전트 투입 방식

**병렬 투입**: 4개 에이전트를 동시에 실행하여 각자의 관점에서 독립 분석 → PM이 종합 보고서 작성

```
[Code Reviewer] ──┐
[Backend Dev]   ──┼── 병렬 실행 ──→ [PM 종합 보고서] ──→ 사용자 판단
[Security Res.] ──┤
[Test Engineer] ──┘
```

## 4. 사람 vs AI 역할 분담

### 사람이 담당한 것

| 작업 | 내용 |
|------|------|
| **아키텍처 설계 판단** | 7단계 Guard 체인 구성, 보안 레이어 순서 결정 |
| **에이전트 프로세스 설계** | 5개 에이전트 역할 정의, REJECT→APPROVE 사이클 설계 |
| **기능 우선순위** | P0/P1/P2 분류, 작업 순서 결정 |
| **실 브라우저 테스트** | Playwright headless가 못 찾은 런타임 버그 5건 발견 |
| **최종 판단** | 모든 에이전트 분석 결과를 보고 수정/승인/거부 결정 |
| **UI/UX 피드백** | "탭이 안 보인다", "버튼 색이 안 변한다" 등 실사용 관점 피드백 |
| **프로젝트 방향 전환** | "AI 활용 프로젝트로 리디자인하자" 등 전략적 판단 |

### AI가 담당한 것

| 작업 | 내용 |
|------|------|
| **코드 구현** | Guard, Service, Controller, Middleware, 프론트엔드 |
| **테스트 작성** | 174 unit + 28 E2E |
| **보안 분석** | 취약점 발견 (Critical 2 + High 4 → 전부 수정) |
| **코드 리뷰** | 타입 안전성, 패턴 일관성, dead code 탐지 |
| **문서 작성** | README (영문+한글), CHANGELOG, REFACTORING_HISTORY |
| **침투 테스트** | 10개 시나리오 자동화 (100% 방어율 확인) |
| **버그 수정** | 에이전트가 발견한 이슈 즉시 수정 |

### AI가 못 하고 사람이 한 것

| 항목 | 설명 |
|------|------|
| **IPv6 토큰 파싱 버그** | 단위 테스트는 IPv4만 사용 → 실 브라우저(localhost = `::1`)에서 발견 |
| **Cookie URL-encoding** | mock 테스트는 raw string → 실제 브라우저는 `:`를 `%3A`로 인코딩 |
| **fetch() Set-Cookie 미적용** | 단위 테스트에서는 정상 → 실제 브라우저 보안 정책으로 쿠키 미저장 |
| **Rate limit 충돌** | 단위 테스트에서는 Guard 단독 → 실제로는 글로벌 ThrottlerGuard가 먼저 소진 |
| **WebSocket 인증 누락** | UI에서 로그인 후 WS 재연결 필요 → 직접 사용해봐야 발견 |

**교훈**: AI가 작성한 코드도 반드시 실 환경에서 사람이 검증해야 한다. Mock 기반 테스트는 브라우저/네트워크 동작을 완벽히 재현하지 못한다.

## 5. 품질 관리 프로세스

### REJECT → APPROVE 사이클 (JS Challenge 예시)

```
1차 분석: CRITICAL 2 + HIGH 4 → REJECT
  ↓ A그룹 수정 (7건)
2차 분석: 수정 확인, MEDIUM 잔존 → CONDITIONAL
  ↓ B그룹 수정 + 테스트 47개
3차 분석: 전부 해결 → APPROVE
  ↓ 실 브라우저 테스트
4차 분석: 런타임 버그 5건 → CONDITIONAL
  ↓ 수정 + 회귀 테스트 추가
5차 분석: Security Researcher STRONG → APPROVE ✅
```

### 에이전트 간 합의 패턴

4개 에이전트가 독립 분석 → PM이 **합의된 이슈**만 수정 대상으로 선정:

- **4/4 합의**: 즉시 수정 (예: x-api-key 무검증 bypass)
- **3/4 합의**: 우선 수정 (예: XSS in HTML template)
- **2/4 합의**: 권장 수정 (예: DTO @MaxLength)
- **1/4만 지적**: 다음 이터레이션으로 연기

이 방식으로 **"에이전트 하나의 의견"이 아닌 "팀의 합의"**를 기반으로 판단.

## 6. 효율화 제안 (다음 프로젝트용)

### DO

| 전략 | 효과 |
|------|------|
| **변경 범위에 맞는 에이전트만 투입** | 작은 수정은 관련 에이전트 1~2개만 (비용 60% 절감) |
| **수정 사항을 모아서 한 번에 분석** | 건건이 분석하지 말고 A+B 그룹 묶어서 1회 (라운드 수 절반) |
| **실 브라우저 테스트를 먼저** | AI 분석 전에 실 환경 테스트 → 런타임 이슈 선발견 |
| **PM 에이전트를 마지막에만** | 매 라운드가 아닌 주요 마일스톤에서만 PM 보고서 |

### DON'T

| 패턴 | 문제 |
|------|------|
| **매 커밋마다 심층분석** | 비용 과다. 기능 완성 후 1회로 충분 |
| **4개 에이전트 항상 전원** | 문서 수정에 Security Researcher 불필요 |
| **같은 이슈 반복 확인** | "이전 라운드에서 확인된 사항은 스킵" 지시 필요 |

## 7. 최종 평가

### AI 활용 효과

| 지표 | 수치 |
|------|------|
| **AI 없이 추정 개발 기간** | 3~4주 (1인 기준) |
| **AI 활용 실제 기간** | 5일 |
| **속도 향상** | ~4~5배 |
| **발견된 보안 취약점** | 11건 (Critical 2 + High 4 + Medium 5) |
| **취약점 수정 완료율** | 100% |
| **테스트 커버리지** | 174 unit + 28 E2E (AI 작성) |
| **침투 테스트 방어율** | 100% (10/10) |
| **거짓 차단율** | 0% (7/7 정상 사용자 시나리오) |

### 핵심 교훈

1. **AI는 "시니어 팀"이 될 수 있다** — 단, 역할을 명확히 정의하고 프로세스를 설계해야 한다
2. **AI의 테스트는 Mock 수준** — 실 환경 검증은 반드시 사람이 해야 한다
3. **비용의 60%는 반복 분석** — 효율적 투입 전략이 중요하다
4. **REJECT→APPROVE 사이클이 품질을 만든다** — 한 번에 완벽한 코드는 없다
5. **AI 활용을 숨기지 말고 프로세스를 보여라** — 투명한 AI 활용이 더 강한 어필이 된다

## 8. 결론 — 돈을 어디서 태웠고, 어떻게 줄일 수 있었나

### 솔직히 말하면

돌이켜보니까 비용의 절반 이상은 안 써도 됐다. 뭘 고쳤든 간에 "심층분석해줘"를 너무 자주 했다. 코드 한 줄 고치고 4개 에이전트 전원 출동시키고, 걔네가 20개 파일 전부 다시 읽고, 저번에 이미 OK 받은 것도 또 확인하고. 이걸 10번 반복했으니까 결국 에이전트를 40번 부른 셈이다.

가장 아까웠던 건 이거다 — JS Challenge 구현하고 AI한테 3번이나 분석 돌렸는데, 정작 실제 브라우저에서 돌려보니까 AI가 못 찾은 버그가 5개 나왔다. IPv6 콜론 문제, 쿠키 인코딩, fetch에서 Set-Cookie 안 먹히는 거... 전부 브라우저를 한 번만 먼저 켜봤으면 AI 분석 2라운드를 아낄 수 있었다.

### 다음에는 이렇게 할 것

**먼저 직접 돌려보기.** AI한테 "분석해줘" 하기 전에 일단 브라우저 켜고, curl 쏘고, 눈으로 확인. 명백한 문제는 사람이 더 빨리 찾는다. 그 다음에 AI한테 넘기면 "이건 돌아가는데 보안적으로 괜찮아?" 수준의 질문만 하면 된다.

**에이전트 전원 출동은 마일스톤에서만.** 문서 좀 고쳤다고 Security Researcher를 부를 필요 없다. 테스트만 추가했으면 Test Engineer만 확인하면 된다. "이 변경이 누구 영역이지?"를 먼저 생각하고 해당 에이전트만 부르자.

**고칠 거 있으면 모아서 한 번에.** 이슈 하나 고치고 분석, 또 하나 고치고 분석, 이러면 라운드만 늘어난다. 3개 모아서 한 방에 수정하고 한 번만 분석 돌리면 같은 결과를 1/3 비용으로 얻는다.

**"저번에 OK 받은 건 넘어가"라고 말해주기.** 에이전트는 매번 백지에서 시작하니까, 이전 라운드 결과를 프롬프트에 넣어줘야 한다. 안 그러면 이미 확인된 걸 또 확인하면서 토큰을 태운다.

### 숫자로 보면

실제로 쓴 것: 에이전트 ~40회, 10라운드, 매번 4개 전원

이렇게 했으면: 에이전트 ~8회, 3라운드, 필요한 1~2개만

결과물은 같은데 비용은 70~80% 줄었을 것이다. 다음 프로젝트(공격 스크래퍼)에서는 이 교훈 그대로 적용할 생각이다.
