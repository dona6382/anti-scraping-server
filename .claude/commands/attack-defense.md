이 프로젝트는 anti-scraping 방어 서버야. $ARGUMENTS 라운드에 걸쳐 공격자/방어자 양쪽 역할을 반복해. (기본: 5라운드)

## 프로세스 (매 라운드)
1. 🔴 공격: 코드 분석 + 브라우저 실전 공격을 병렬로 실행. 실제 exploit 가능한 것만 보고
2. 🔵 방어: 발견된 HIGH 이상 이슈 즉시 수정 + npm test + tsc 확인
3. 🟢 개선: 공격 시도에서 배운 것을 바탕으로 방어 로직 자체를 강화 (새 탐지 규칙, 임계값 조정, 로깅 보강 등)
4. 📝 학습: 이번 라운드에서 막힌/뚫린 것을 기록 → 다음 라운드 공격/방어에 반영

## 라운드별 테마
- R1: 인증/세션 — 쿠키 위조, 토큰 재사용, JWT 조작 → 방어 후 인증 체계 강화
- R2: 봇 탐지 회피 — Guard 체인 우회, fingerprint 스푸핑, rate limit 회피 → 방어 후 탐지 정확도 개선
- R3: 인프라 공격 — DoS, 메모리 고갈, 캐시 조작, 설정 오류 → 방어 후 안정성 강화
- R4: 복합 공격 — R1~R3 수정사항 간 상호작용 버그, 다단계 공격 시나리오 → 방어 후 통합 검증
- R5: 최종 펜테스트 — 모든 개선사항 대상 전면 재공격. CLEAN이면 성공

## 방어 개선 범위 (수정뿐 아니라 강화)
- 취약점 수정은 기본. 추가로:
  - 새 공격 패턴에 대한 탐지 규칙 추가
  - Guard 임계값/가중치 튜닝
  - 로깅/모니터링 보강 (공격 가시성)
  - 테스트 케이스 추가 (재발 방지)

## False Positive 방지
- Node.js 싱글스레드 → 동기 코드 race condition 아님
- HMAC-SHA256 + 64바이트 키 → brute force 불가
- HTTPS 전제 → 평문 전송 이슈 아님
- 설계 의도된 동작은 취약점이 아님 (PUZZLE_THRESHOLD=0, 10s 타이머, MIN_REQUESTS=5 등)
- Memory cache getAndDelete는 싱글스레드에서 원자적
- returnUrl은 pathname만 사용 (hostname 무시) → open redirect 아님

## 조기 종료
- CRITICAL/HIGH 0건 + 방어 개선할 것도 없으면 해당 라운드에서 종료
- 커밋은 마지막에 항목별로

## 출력 형식
각 라운드:
R{N} 🔴 공격: {발견 수}건 — {핵심}
R{N} 🔵 방어: {수정 수}건 — {핵심}
R{N} 🟢 개선: {강화 내용 1줄}
또는: `R{N}: CLEAN — 추가 개선 없음`
